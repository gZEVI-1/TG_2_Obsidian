# Этап 8: RAG — семантический поиск по заметкам

## Этап

Этап 8 — поиск по смыслу поверх полнотекстового поиска (FR-09 из
[FEATURES.md](FEATURES.md)). RAG здесь не заменяет обычный поиск, а дополняет
его: если по словам ничего не нашлось или нашлось мало, бот ищет заметки,
близкие по смыслу.

## Цель

Находить заметку, даже когда пользователь не помнит её названия и точных слов:
«что я писал про сроки релиза» должно находить заметку «Проект Альфа», где
слова «сроки релиза» не встречаются. Работать это должно локально, без
облачных эмбеддингов и без правок хранилища.

## Что сделано

- `app/rag.py` — весь RAG в одном модуле:
  - `chunk_text()` — делит заметку на фрагменты ≤ 900 символов по абзацам;
    слишком длинный абзац режется принудительно; заголовок заметки
    добавляется к фрагменту перед эмбеддингом, чтобы модель видела тему;
  - `LocalEmbedder` — модель `sentence-transformers`, грузится лениво и один
    раз, `encode` выполняется в отдельном потоке (не блокирует обработку
    Telegram), векторы нормализованы — косинус считается скалярным
    произведением;
  - `RagIndex` — векторы фрагментов (numpy) и их тексты; хеши заметок для
    инкрементального обновления; атомарная запись `index.json` + `vectors.npy`;
    битый индекс не роняет бота — пересобирается;
  - `SemanticSearch` — `refresh()` обновляет индекс, `search()` возвращает
    заметки по косинусу с лучшим фрагментом и оценкой;
  - `store_dir()` — у каждого хранилища своя папка индекса
    (`state/rag/<hash>/`), поэтому переключение vault не смешивает данные.
- `app/config.py` — настройки с валидацией:
  - `RAG_ENABLED` (по умолчанию `true`) — выключатель семантического поиска;
  - `RAG_MODEL` (по умолчанию
    `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`) — модель;
  - `RAG_TOP_K` (1–20, по умолчанию 5) — сколько заметок по смыслу добавлять.
  Все три видны в `--check-config`.
- `app/agent.py` — `Agent(..., semantic=...)`; `_search` сначала делает
  обычный поиск (имена, опечатки, текст), затем добивает результаты
  совпадениями по смыслу, пока не исчерпан `AGENT_SEARCH_LIMIT`. Дубли
  отбрасываются, смысловые строки помечены «по смыслу». Если RAG упал
  (нет модели, нет сети при первом скачивании), ошибка пишется в лог, а поиск
  отвечает как раньше.
- `app/bot.py`:
  - при старте создаётся `SemanticSearch`, индекс обновляется фоновой
    задачей — запуск бота не ждёт загрузку модели;
  - `/rag` — состояние: модель, сколько заметок и фрагментов в индексе, когда
    обновлён;
  - `/reindex` — ручное обновление индекса с отчётом (обновлено, без
    изменений, удалено, ошибки);
  - если зависимостей нет или `RAG_ENABLED=false`, в лог пишется
    предупреждение, бот работает как до этапа;
  - при остановке фоновая задача отменяется, хранилище закрывается.
- `app/__main__.py` — `--check-rag`: строит индекс на текущем хранилище,
  делает пробный запрос и печатает найденные заметки с оценками.
- `requirements-rag.txt` — `sentence-transformers` и `numpy` отдельно от
  основного `requirements.txt`: базовый бот остаётся лёгким, RAG ставится по
  желанию.
- `.gitignore` — `state/` целиком: индекс — производный кэш, в git не нужен.
- `tests/test_rag.py` — 16 тестов: нарезка текста, сборка индекса, поиск по
  смыслу, инкрементальное обновление (без изменений, изменённая, удалённая
  заметка), сохранение и чтение после перезапуска, пустой индекс, настройки.
- `docs/` — этот файл, обновлённые [README.md](README.md),
  [DECISIONS.md](DECISIONS.md) (ADR-36), [FEATURES.md](FEATURES.md)
  (таблица настроек).

## Внешние действия

Один раз поставить зависимости и скачать модель (это делает сам
`sentence-transformers` при первом запуске):

```powershell
cd E:\FOLDER\TG-OBS\TG_2_Obsidian
.\.venv\Scripts\python.exe -m pip install -r requirements-rag.txt
.\.venv\Scripts\python.exe -m app --check-rag
```

Модель занимает ~470 МБ в кэше HuggingFace (`%USERPROFILE%\.cache\huggingface`)
и качается только при первом `--check-rag` или старте бота. Дальше всё
работает офлайн.

## Принятые решения

- **Локальные эмбеддинги** (ADR-36). Выбран вариант без облака: нет оплаты,
  нет передачи заметок наружу, работает офлайн. Цена — зависимость от torch и
  модель на диске; на слабом CPU индексация идёт минуты, поэтому она
  инкрементальная и в фоне.
- **Индекс на numpy, а не ChromaDB** (ADR-36). Для личного хранилища (до 500
  заметок, несколько тысяч фрагментов) достаточно матрицы векторов и
  скалярного произведения: нет второй БД, сервиса, схемы и миграций.
  ChromaDB оправдана на десятках тысяч фрагментов — тогда её можно добавить
  за тем же интерфейсом `SemanticSearch`.
- **Индекс — производный кэш.** Его можно удалить, он пересоберётся; хеши
  заметок позволяют обновлять только изменённое. В git он не попадает.
- **RAG дополняет, а не заменяет поиск** (FR-09). Первым всегда идёт обычный
  поиск по именам и тексту — он предсказуем и мгновенный; семантика только
  добивает список. Если RAG недоступен, поведение не меняется.
- **Инкрементальность по хешу содержимого, а не по времени файла**: REST API
  не отдаёт mtime, хеш работает одинаково в обоих режимах хранилища.
- **Семантика — только в диалоговом поиске агента.** Кнопочные сценарии
  («Найти», «Дописать») продолжают искать по именам: это предсказуемо и не
  требует держать индекс модели в горячем состоянии для каждого нажатия.
  При необходимости сценарии можно подключить к тому же `SemanticSearch`.
- **Multilingual-модель**, потому что заметки на русском, а часть имён и
  текстов — на английском. Модель симметричная, без префиксов «query/passage»,
  поэтому индекс и запрос считаются одинаково.

## Как проверить

```powershell
cd E:\FOLDER\TG-OBS\TG_2_Obsidian
.\.venv\Scripts\python.exe -m unittest discover -s tests   # 138 тестов OK
.\.venv\Scripts\python.exe -m app --check-config           # rag_* настройки
.\.venv\Scripts\python.exe -m app --check-rag              # модель, индекс, пробный поиск
```

`--check-rag` в логе показывает «RAG-индекс: заметок N, фрагментов M» и
несколько найденных заметок с оценками. Полезно, что индекс не пустой:
`заметок > 0`.

В Telegram:

1. `/rag` → модель, число заметок и фрагментов, дата обновления.
2. `/reindex` → «RAG-индекс готов…», повторный запуск — «без изменений: N».
3. «Что я писал про сроки релиза?» при отсутствии этих слов в заметке →
   в ответе появляются строки вида `- Projects/Проект Альфа.md: … (по смыслу)`.
4. Добавить заметку, выполнить `/reindex` → счётчик заметок вырос.
5. `RAG_ENABLED=false` и перезапуск → `/rag` пишет, что поиск выключен;
   обычный поиск и бот работают.

## Риски и откат

- **Первый запуск требует сети.** Модель скачивается один раз (~470 МБ); без
  сети RAG не запустится, но бот продолжит работать с обычным поиском — это
  видно в логе и `/rag`.
- **Место на диске.** Модель ~470 МБ в кэше пользователя, индекс —
  единицы-десятки МБ в `state/rag/`. Удаление `state/rag/` безопасно.
- **CPU и память.** torch на Windows занимает заметную память; на слабом NAS
  обновление индекса может идти минуты. Поэтому оно инкрементальное и
  фоновое, а поиск по индексу — это только матричное умножение.
- **Смысловой поиск может ошибаться.** Он ранжирует по близости, а не по
  истине: похожие по теме заметки могут оказаться выше. Поэтому результат —
  список кандидатов, а решение (читать/дописывать) принимает модель или
  пользователь.
- **Индекс стареет.** Между обновлениями поиск видит старые версии заметок;
  обновление — фоновое при старте или по `/reindex`. При частых правках
  полезно запускать `/reindex` после крупных изменений.
- **Смена хранилища.** Индекс привязан к пути/адресу хранилища: после смены
  vault строится новый, старый не мешает и удаляется вручную.
- **Откат:** `RAG_ENABLED=false` (без удаления пакетов) или
  `pip uninstall sentence-transformers torch` + удалить `state/rag/`.
  Данные в хранилище RAG не меняет вообще — только читает.
