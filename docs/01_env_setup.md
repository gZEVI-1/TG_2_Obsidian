# Этап 1: Каркас проекта и конфигурация

## Этап

Этап 1 — каркас проекта, виртуальное окружение, конфигурация из `.env`,
логирование без секретов.

## Цель

Получить минимальный скелет проекта, который запускается одной командой и
проверяет, что все настройки читаются правильно. Никакой бизнес-логики,
Telegram и Obsidian на этом этапе нет.

## Что сделано

- Проект размещён в клоне git-репозитория `E:\FOLDER\TG-OBS\TG_2_Obsidian`
  (remote `gZEVI-1/TG_2_Obsidian`). Код, документация и `.env.example` лежат
  в корне репозитория.
- Создано виртуальное окружение `.venv` внутри репозитория (Python 3.14.4),
  установлен `python-dotenv`.
- В `.env` ключ Obsidian переименован из `Obs_rest_api` в `OBSIDIAN_API_KEY`;
  значение не менялось. Резервная копия исходного файла — `E:\FOLDER\.env.bak`
  (вне репозитория, чтобы секрет не попал в git).
- `app/__init__.py` — пакет приложения.
- `app/config.py`:
  - `Settings` — неизменяемый dataclass со всеми настройками проекта;
  - `load_settings()` — читает `.env` (если есть) и переменные окружения;
  - `safe_summary()` — представление настроек для логов: секреты показываются
    как `<задан, N симв.>`, значения не раскрываются;
  - `_env_bool()` — строгий разбор `true/false`, на мусор падает с понятной
    ошибкой;
  - проверка `LOG_LEVEL` по списку допустимых значений.
- `app/logging_setup.py` — `setup_logging(level)`: единый формат строки лога,
  вывод в stdout, принудительный UTF-8 для консоли Windows.
- `app/__main__.py` — точка входа `python -m app`: загружает настройки,
  печатает безопасную сводку и предупреждение, если `OBSIDIAN_DRY_RUN=false`.
- `requirements.txt` — `python-dotenv>=1.0,<2` (позже дополнен `aiogram` и
  `aiohttp` на Этапах 2–3).
- `.env.example` — шаблон всех переменных с комментариями.
- Собственный `.gitignore` не создавался: в репозитории уже есть стандартный
  Python-`.gitignore`, он исключает `.env` и `.venv/` (проверено:
  `git status` не показывает эти файлы).

## Внешние действия

Не требовались для кода. Пользователь параллельно подготовил инфраструктуру:

- клонировал репозиторий `TG_2_Obsidian` в `E:\FOLDER\TG-OBS`;
- создал тестовый vault `E:\FOLDER\TG-OBS\TG-OBS-vault-test`, установил плагин
  Local REST API, включил HTTP-сервер на порту 27123, ключ сгенерирован.

По итогам уточнения проект перенесён в репозиторий, ключ в `.env` переименован
(см. «Что сделано»).

## Принятые решения

- Конфигурация без `pydantic`/`pydantic-settings`: хватает модуля `os` и
  `python-dotenv`, меньше зависимостей на старте. Если появится сложная
  валидация (вложенные структуры, списки), вернёмся к вопросу.
- Все секреты — только в `.env`; документация и логи содержат лишь факт
  наличия секрета и его длину.
- `OBSIDIAN_DRY_RUN` по умолчанию `true`: защита от случайной записи в vault
  ещё до появления кода записи.
- Логирование настраивается до чтения `.env`, а уровень уточняется после.
  Иначе предупреждение «`.env` не найден» выводилось бы без формата и в
  кодировке консоли (на Windows — с «кракозябрами»).
- `LOG_LEVEL` и `DRY_RUN` валидируются строго, а не «молча подставляются»:
  опечатка должна проявляться сразу.
- `aiogram` пока не в `requirements.txt` — он появится на Этапе 2 вместе с
  кодом бота.
- Корень проекта — корень git-репозитория `TG_2_Obsidian`, а не папка
  `E:\FOLDER\TG-OBS`: вложенный репозиторий внутри нерепозиторной папки
  усложнил бы коммиты и перенос на NAS.

## Как проверить

Все команды выполняются из корня репозитория `E:\FOLDER\TG-OBS\TG_2_Obsidian`.

```powershell
# 1. Запуск: настройки читаются из .env реального проекта
.\.venv\Scripts\python.exe -m app --check-config
#    (флаг появился на Этапе 2; до него хватало обычного запуска)

# 2. Проверить, что секреты не утекают в лог (тот же запуск)
#    Для секретов ожидается «<задан, N симв.>», значения не выводятся.
```

Ожидается: строки лога с таймстампом, `config OK` в конце, для секретов —
`<задан, N симв.>` или `<не задан>`, значения токенов в выводе отсутствуют.
При `LOG_LEVEL=VERBOSE` или `OBSIDIAN_DRY_RUN=maybe` — `ValueError` с
объяснением, что именно неверно.

## Риски и откат

- Риск: случайный коммит `.env`. Защита — существующий `.gitignore` репозитория
  (`.env` и `.venv/` в нём есть); проверять `git status` перед коммитом.
- Риск: секрет попадёт в лог через сообщение об ошибке сторонней библиотеки.
  Правило проекта: секреты не подставляются в тексты исключений.
- Откат: удалить `.venv`, `app/`, `docs/`, `requirements.txt`, `.env.example`
  и вернуть `.env` из резервной копии `E:\FOLDER\.env.bak`. Данные vault не
  затрагивались.
