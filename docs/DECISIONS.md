# Журнал архитектурных решений (ADR-lite)

Короткие записи о ключевых решениях: контекст, решение, последствия.
Нумерация сквозная, записи не удаляются — устаревшие помечаются как заменённые.

## ADR-01: Документирование каждого этапа в `docs/`

**Контекст.** Проект ведётся поэтапно, между этапами возможны паузы. Нужно
понимать состояние проекта, не читая код.

**Решение.** Один md-файл на этап (`docs/NN_<название>.md`) с обязательными
разделами, оглавление в `docs/README.md`, решения — в этом файле.

**Последствия.** Документация обновляется в том же этапе, где меняется код.
Стоимость: немного времени на каждый этап. Выгода: вход в проект и откат без
чтения кода.

## ADR-02: Один OpenAI-совместимый слой доступа к LLM

**Контекст.** Нужен бесплатный или очень дешёвый внешний провайдер с
возможностью быстро менять модель и провайдера.

**Решение.** Все обращения к LLM идут через один HTTP-клиент к
OpenAI-совместимому эндпоинту. Провайдер, базовый URL, ключ и модель задаются
только переменными `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.

**Последствия.** Смена модели — правка `.env` и перезапуск, без изменений кода.
Ограничение: доступны только провайдеры с OpenAI-совместимым API. Качество
tool-calling зависит от выбранной модели — проверяется на Этапе 4.

## ADR-03: Кроссплатформенность (Windows → NAS)

**Контекст.** Сейчас запуск на Windows-ПК, позже перенос на NAS (Linux).

**Решение.** Никаких Windows-специфичных вызовов и путей: `pathlib`, работа с
кодировками через явный UTF-8, конфигурация только через переменные окружения.

**Последствия.** Перенос сводится к установке Python и копированию проекта с
`.env`. Контейнеризация (Docker) отложена до этапа переноса.

## ADR-04: RAG откладывается

**Контекст.** Задача — создавать заметки и ставить связи. Семантический поиск
требует эмбеддингов, векторной БД и инкрементальной индексации.

**Решение.** На первых этапах связи ставятся по именам файлов, алиасам и тегам.
Эмбеддинги и ChromaDB — отдельный опциональный Этап 8.

**Последствия.** Меньше зависимостей и точек отказа. Ограничение: поиск «по
смыслу» появится позже; возможен переход на Python 3.12 в venv из-за
совместимости пакетов.

**Дополнено ADR-18.** До RAG поиск заметок — полнотекстовый; RAG остаётся
опциональным Этапом 8.

## ADR-05: Тестовый vault и dry-run по умолчанию

**Контекст.** Запись в Obsidian необратима, ошибка агента может испортить
рабочее хранилище.

**Решение.** Разработка и проверки — только на тестовом vault.
`OBSIDIAN_DRY_RUN=true` по умолчанию: операции записи логируются, но не
выполняются. Рабочий vault подключается последним, по явному разрешению.

**Последствия.** Часть проверок требует двух прогонов (dry-run и реальная
запись). Зато агент нельзя случайно направить в рабочее хранилище.

## ADR-06: Конфигурация без pydantic

**Контекст.** На Этапе 1 нужны плоские настройки из `.env`.

**Решение.** `dataclass` + `os.environ` + `python-dotenv`, ручная валидация
`LOG_LEVEL` и булевых значений.

**Последствия.** Одна зависимость вместо трёх, прозрачное поведение. Если
появятся вложенные структуры или списки, вернёмся к `pydantic-settings` по
согласованию.

## ADR-07: Корень проекта — клон репозитория `TG_2_Obsidian`

**Контекст.** Рабочая папка `E:\FOLDER\TG-OBS` не является репозиторием, а код
должен версионироваться. Пользователь клонировал в неё свой репозиторий
`gZEVI-1/TG_2_Obsidian` (пустой, только `README` и `LICENSE`).

**Решение.** Корень проекта — `E:\FOLDER\TG-OBS\TG_2_Obsidian`. Код, `docs/`,
`requirements.txt`, `.env.example` лежат в корне этого репозитория. Собственный
`.gitignore` не добавлялся: в репозитории уже есть стандартный Python-шаблон,
исключающий `.env` и `.venv/`. Ключ Obsidian в `.env` приведён к
`OBSIDIAN_API_KEY` (было `Obs_rest_api`). Тестовое хранилище
`TG-OBS-vault-test` остаётся отдельной папкой рядом и в git не попадает.

**Последствия.** Один репозиторий, один `.venv`, коммиты из корня проекта.
Секреты по-прежнему только в `.env` вне контроля версий.

## ADR-08: Имена переменных окружения в едином стиле

**Контекст.** В `.env` пользователя ключ Obsidian назывался `Obs_rest_api`.

**Решение.** Все переменные — в `UPPER_SNAKE_CASE` с префиксом подсистемы:
`TELEGRAM_*`, `LLM_*`, `OBSIDIAN_*`.

**Последствия.** Совпадение имён с `.env.example` и кодом, меньше опечаток.
Переименование выполнено один раз на Этапе 1; резервная копия старого файла
лежит вне репозитория.

## ADR-09: Long polling вместо webhook

**Контекст.** Бот запускается на домашнем ПК за NAT: нет публичного адреса,
нет домена и сертификата для входящих HTTPS-запросов Telegram.

**Решение.** `Dispatcher.start_polling()`. Webhook не используется.
Перед polling вызывается `delete_webhook(drop_pending_updates=True)`, чтобы
старый webhook не блокировал получение обновлений.

**Последствия.** Ноль настроек на стороне сети, запуск одной командой.
Ограничение: бот работает только пока запущен процесс; на NAS при переносе
вернёмся к вопросу (возможен webhook + reverse proxy).

## ADR-10: Запись в vault только без молчаливой перезаписи

**Контекст.** Агент будет создавать заметки по тексту пользователя. Имя,
предложенное LLM, легко совпадёт с существующей заметкой; `PUT` в Local REST API
перезаписывает файл без вопросов.

**Решение.** `ObsidianClient.write_note()` по умолчанию проверяет существование
файла и при совпадении бросает `ObsidianError`. Перезапись — только явным
`overwrite=True`. В dry-run клиент не отправляет изменяющих запросов вообще.

**Последствия.** Потеря заметки из-за совпадения имени исключена на уровне
клиента, а не «внимательности промпта». Цена: лишний `GET` перед записью.

**Дополнено ADR-16.** Изменение существующей заметки выполняется через
read-modify-write, а не полной перезаписью.

## ADR-11: `aiohttp` как HTTP-клиент

**Контекст.** Нужны запросы к Obsidian REST API из асинхронного бота.
`aiohttp` уже установлен как зависимость aiogram.

**Решение.** Использовать `aiohttp` напрямую: одна `ClientSession` на клиент,
таймаут 10 секунд, `Authorization: Bearer`.

**Последствия.** Нет блокировки event loop и лишних зависимостей. Ограничение:
`requests` в проекте не используется, синхронные утилиты писать не будем.

## ADR-12: OpenRouter и бесплатная модель на этапе разработки

**Контекст.** Нужна модель с поддержкой tool-calls и нулевым бюджетом на время
разработки, с возможностью быстро сменить модель или провайдера.

**Решение.** Провайдер — OpenRouter (`https://openrouter.ai/api/v1`), модели
с суффиксом `:free`. Код не знает о провайдере: только `LLM_BASE_URL`,
`LLM_API_KEY`, `LLM_MODEL` (ADR-02). Текущая модель —
`nvidia/nemotron-3-ultra-550b-a55b:free`: `google/gemma-4-31b-it:free` трижды
подряд отдала `429` от Google AI Studio (ограничение общего пула, не ключа).

**Последствия.** Ноль расходов на этапе разработки. Ограничения: 20 запросов
в минуту и 50 в сутки при покупке кредитов менее $10 (1000 при $10+); модели
исчезают и перегружаются — лечится строкой в `.env`. Провайдеры бесплатных
моделей могут обучаться на промптах, поэтому до решения вопроса приватности
используется только тестовый vault. Переход на платную модель или другого
провайдера — правка `.env`, без изменений кода.

## ADR-13: Бот без истории диалога до Этапа 5

**Статус.** Заменено ADR-14: после первой живой проверки пользователь попросил
сохранять контекст и начинать новый чат командой `/new`.

**Контекст.** На Этапе 4 задача — доказать, что модель отвечает и умеет
tool-calls, а не построить память диалога.

**Решение.** Каждое сообщение — отдельный запрос: системный промпт + текст
пользователя, без предыдущих реплик. История и цикл вызова инструментов
появляются на Этапе 5 вместе с агентом.

**Последствия.** Бот «не помнит» предыдущие сообщения — это ожидаемое
поведение этапа, а не баг. Меньше кода, который придётся переписывать: агент
всё равно вводит собственный цикл и хранение истории. Ограничение по контексту
модели пока не актуально.

## ADR-14: История диалога в памяти процесса и команда `/new`

**Контекст.** После первого запуска бот отвечал на каждое сообщение как на
первое: каждая реплика — отдельный запрос без предыдущих. Пользователь
попросил, чтобы контекст сохранялся, а новый диалог начинался по команде
`/new` — иначе бот не может ссылаться на сказанное ранее.

**Решение.** `ChatMemory` в `app/bot.py`: словарь `chat_id → список сообщений`,
ключ — `chat_id`, чтобы в будущем поддержать несколько пользователей.
Хранятся последние 20 сообщений (10 пар «пользователь — модель»), старое
отбрасывается. В каждый запрос уходит системный промпт, затем история, затем
новое сообщение. `/new` очищает историю этого чата. `/start` тоже очищает
историю — по просьбе пользователя: «начать заново» должна уметь одна из
основных команд, а не только `/new`. Хранилище — память процесса, без БД.

**Последствия.** Бот помнит контекст в рамках запущенного процесса;
перезапуск бота историю очищает. Два способа начать заново (`/start`, `/new`)
ведут себя одинаково — расхождения в поведении между ними нет. Память не
ограничена по символам — при очень длинных репликах контекст растёт (для
модели с окном 1M токенов не критично). На Этапе 5 структура расширяется:
в историю попадут сообщения с `tool_calls` и результаты инструментов, а
`/start` и `/new` будут очищать и их. Переход на постоянное хранилище
(SQLite) — Этап 9–10, если понадобится.

## ADR-15: Подтверждение только при неоднозначности

**Контекст.** Пользователь попросил не додумывать за него: при сомнениях бот
должен уточнять. При этом вопрос на каждое действие мешает работе.

**Решение.** Одна глобальная настройка `AGENT_CONFIRMATION`:
`auto` (по умолчанию) — спрашивать только при неоднозначности или высоком
риске; `always` — перед любой записью; `never` — не спрашивать. В `auto`
обязательны подтверждения для: нескольких кандидатов, низкой уверенности,
неясного раздела или папки, создания новой папки, массовой простановки связей
и любых разрушающих операций. Если ответа нет — ничего не записывается.

**Последствия.** Меньше лишних вопросов, но нужны явные критерии уверенности
и тесты сценариев. Настройка одна для всех операций; отдельные переключатели
добавляются только при реальной необходимости.

## ADR-16: Изменение заметки — добавление и правка раздела

**Контекст.** Пользователь выбрал вариант «добавление + правка раздела»:
полная перезапись заметки слишком рискованна.

**Решение.** Изменение выполняется через read-modify-write: клиент читает
заметку, агент добавляет блок в конец или заменяет содержимое выбранного
раздела по заголовку. Frontmatter, остальные разделы и существующие ссылки
сохраняются. Если раздел не найден или подходящих несколько — вопрос
пользователю. Полная замена — только отдельная явная операция с
подтверждением, не по умолчанию.

**Последствия.** Нужен разбор заголовков Markdown и предпросмотр diff.
Local REST API пишет файл целиком, поэтому read-modify-write обязателен;
при одном пользователе гонок нет. Риск потери снижен.

## ADR-17: Автоматическое расположение: Inbox и автоопределение

**Контекст.** Нужно автоматически раскладывать заметки, но структура
хранилища у пользователя может меняться; угадывание папки недопустимо.

**Решение.** После определения заметки бот показывает кнопки «Inbox» и
«Автоопределение». Inbox — папка `AGENT_DEFAULT_FOLDER` (по умолчанию
`Inbox`), создаётся при необходимости. Автоопределение использует список
существующих папок и контекст заметки; при высокой уверенности предлагает
папку, при неоднозначности — варианты и Inbox. Новую папку создаёт только
после подтверждения. Путь проверяется на запрещённые символы и `..`.

**Последствия.** Предсказуемый безопасный вариант по умолчанию; авторежим
требует инвентаризации папок и критериев уверенности. Структура vault
не меняется без согласия.

## ADR-18: Полнотекстовый поиск до RAG

**Контекст.** Для добавления в существующую заметку нужен поиск по
контексту. RAG отложен (ADR-04), эмбеддинги на Этапе 5 не нужны.

**Решение.** Использовать полнотекстовый поиск Obsidian Local REST API
(`POST /search/simple/?query=...`), при недоступности — список файлов
(`GET /vault/`) и чтение кандидатов. Ранжирование: совпадение имени,
алиаса, тега, затем содержимого; LLM выбирает из top-N. Если ничего не
найдено — предложить создать новую заметку.

**Последствия.** Нет новых зависимостей и индекса; качество зависит от
точных слов, а не смысла. RAG (Этап 8) дополняет, а не заменяет поиск.

## ADR-19: Обработка ошибок API и сервера

**Контекст.** Новое требование: ошибки Obsidian/LLM/сети не должны
приводить к падению бота, дублям заметок или молчаливой потере данных.
При проверке Этапа 4 выяснилось, что `answer_text()` ловит только
`LLMError`, а сетевые ошибки `aiohttp` и таймауты всплывали наружу.
Исправлено: `LLMClient` оборачивает их в `LLMError`; для Obsidian
аналогичная обработка входит в FR-08.

**Решение.** Единая классификация: конфигурация/авторизация (`401`/`403`),
не найдено (`404`), конфликт/дубль (`409`), лимит (`429`), сервер (`5xx`),
сеть/таймаут, некорректный ответ. Пользователь получает понятное сообщение
и следующий шаг; подробности — в лог без секретов. Повторы: только для
идемпотентных чтений; записи — без слепых ретраев, сначала проверка
состояния. `429` — с учётом `Retry-After`. Частичная запись не считается
успехом. На Этапе 5 — базовая обработка, на Этапе 9 — расширенные
ретраи/лимиты.

**Последствия.** Больше кода и тестов на ошибки; зато бот не падает и
не создаёт дубли. Dry-run сохраняется.

## ADR-20: Связи: автолинковка и массовая простановка

**Контекст.** Нужны связи при создании/изменении и отдельная операция
«проставить связи во всех заметках» с подтверждением.

**Решение.** Кандидаты — по именам, алиасам, тегам и полному тексту; LLM
выбирает top-N. Ссылки добавляются в раздел `## Связи` в конце заметки в
виде `- [[Заметка]]`; существующие ссылки не дублируются, самоссылки и
ссылки на несуществующие заметки не создаются. При создании/изменении —
автоматически, если `AGENT_AUTO_LINK=true`; при неоднозначности — вопрос.
Массовая операция строит план, показывает сводку и требует подтверждения
(кроме `AGENT_CONFIRMATION=never`), выполняется пакетами, идемпотентна.
Inline-ссылки в тексте — отдельная будущая опция, по умолчанию не
используются.

**Последствия.** Связи видимы и не портят авторский текст; повторный запуск
не создаёт дублей. Формат раздела можно пересмотреть после практики.

## ADR-21: Ожидание подтверждения привязано к сообщению

**Контекст.** Кнопки «Подтвердить» / «Отменить» остаются в истории чата.
Пользователь может нажать старую кнопку или дважды подряд одну и ту же.
Без привязки к сообщению бот записал бы «не ту» заметку или создал дубль.

**Решение.** Ожидающее действие хранится по `chat_id` вместе с `message_id`
сообщения, к которому прикреплены кнопки. Обработчик кнопки срабатывает,
только если идентификатор совпадает; при подтверждении действие удаляется
до записи, поэтому повторный клик получает «предложение устарело».
`/new` и `/start` очищают ожидание вместе с историей.

**Последствия.** Двойной клик и старые кнопки безопасны. Ожидание живёт
в памяти процесса: перезапуск бота его теряет, и кнопки старого сообщения
перестают работать — это ожидаемо. При необходимости постоянное хранилище
появится на Этапе 9–10.

## ADR-22: Дописывание по смыслу и защита от дублей

**Контекст.** Первая версия `append_note` всегда писала в конец файла: при
нескольких разделах текст оказывался не на месте, а повторная просьба
создавала копию абзаца.

**Решение.** Инструмент принимает необязательный `section`; модель сначала
читает заметку и указывает раздел, к которому текст относится по смыслу.
Бот дописывает в конец этого раздела (`append_to_section`), а если раздела
нет — в конец заметки. Перед записью текст сравнивается с содержимым заметки
без учёта регистра и пробелов (`contains_text`); при совпадении запись не
выполняется и пользователь видит «такой текст уже есть». Список и проза
склеиваются по-разному: элементы списка — через перевод строки, абзацы —
через пустую строку.

**Последствия.** Текст попадает в осмысленное место, повторные просьбы не
плодят дубли. Ограничение: сравнение точное — перефразированный дубль
не распознаётся; нечёткое сравнение — при необходимости на Этапе 9.


## ADR-23: Пул LLM — ротация аккаунтов, затем моделей, автосброс

**Контекст.** Один бесплатный аккаунт упирается в дневной лимит, и бот
перестаёт отвечать. Пользователь готов добавить несколько API-ключей с разных
аккаунтов, а модели различаются по качеству.

**Решение.** `LLMPool` хранит упорядоченный по качеству список моделей и
список аккаунтов. Лимит считается по паре «модель — аккаунт»: при `429`/`402`
пул перебирает аккаунты текущей модели, затем переходит к следующей модели.
Когда исчерпаны все пары, запоминается ближайший `Retry-After`; к этому
времени автосброс снимает все пометки и возвращает лучшую модель и первый
аккаунт. `401`/`403` отключают аккаунт до сброса. Пока реальных ключей нет,
работает режим заглушек с настраиваемой квотой — он проверяет ту же логику
без сети. Ручные команды: `/llm` (состояние) и `/llm_reset` (сброс).

**Последствия.** Бот переживает исчерпание одного аккаунта и смену модели;
лимиты не тратятся на слепые повторы. Ограничение: состояние пула живёт в
памяти процесса и обнуляется при перезапуске (это же и есть сброс к началу);
общий дневной лимит провайдера на все аккаунты не обходится.

## ADR-24: Поиск по именам — точно и нечётко, затем по тексту

**Контекст.** Встроенный поиск Obsidian ранжирует совпадения по тексту и
ссылкам. Заметка `People/Мария.md` по запросу «мария» оказывалась шестой,
ниже чужих упоминаний о Марии, а опечатка («мрия») не находила ничего.

**Решение.** Отдельный слой `app/search.py` оценивает имена файлов и сегменты
пути: точное имя (1.0), начало имени (0.95), вхождение (0.9), все слова
запроса (0.85), вхождение в путь (0.8), затем нечёткое сходство через
`difflib` с порогом 0.78 (опечатки, другой порядок слов, папка вроде
«Ежедневник»). Именованные совпадения идут первыми, полнотекстовый поиск
`/search/simple/` — после них и только если осталось место в выдаче.

**Последствия.** «мария» и «мрия» находят `Мария.md`, «ежедневнек» — заметки
из папки «Ежедневник». Ограничение: нечёткость по порогу, поэтому совсем
далёкие опечатки не ловятся; сравнение идёт по словам, а не по смыслу
(RAG — Этап 8).

## ADR-25: Внутренний промпт как список команд

**Контекст.** Пользователь часто не называет команду прямо: «запиши это»,
«добавь туда», «поправь». Модель должна сама выбрать действие и не путать
создание с дописыванием.

**Решение.** `SYSTEM_PROMPT` содержит список команд с сигнатурами
(`search_notes`, `list_folders`, `read_note`, `create_note`, `append_note`,
`edit_section`) и правила разбора: разделить просьбу на «что сделать / где /
какой текст», учесть контекст диалога, выбрать команду по смыслу, при
неоднозначности задать один короткий вопрос. Отдельный блок правил письма:
короткое сообщение разворачивается в полноценную заметку (заголовок,
структура), но не копируется дословно и не дополняется выдуманными фактами;
явно присланный готовый текст сохраняется как есть.

**Последствия.** Свободная фраза работает как команда, а кнопки остаются
детерминированным путём без модели. Риск: качество разбора зависит от
модели — на слабой модели возможны неверные команды, поэтому перед записью
всё равно показывается подтверждение.

## ADR-26: Два режима хранилища — REST API и прямые файлы

**Контекст.** Local REST API — плагин внутри Obsidian. В режиме `rest` бот
работает, только пока Obsidian запущен: при закрытом приложении любая команда
заканчивалась ошибкой соединения. Пользователю нужен работающий бот без
постоянно открытого Obsidian.

**Решение.** Введён общий интерфейс `ObsidianBackend` и второй клиент
`VaultClient`, который читает и пишет `.md`-файлы напрямую. Режим выбирается
переменной `OBSIDIAN_MODE`: `auto` (по умолчанию) — `vault` при заданном
`OBSIDIAN_VAULT_PATH`, иначе `rest`; `rest` — Local REST API (поведение
не изменилось); `vault` — файловый режим без HTTP, плагина и ключа. Явный
режим позволяет переключаться, не комментируя путь. Поиск по именам общий,
полнотекстовый в файловом режиме — чтение файлов и поиск подстроки. Файловые
операции идут через `asyncio.to_thread`, запись — через временный файл и
`os.replace`, пути проверяются на выход за пределы vault. Защита от
перезаписи и dry-run сохранены.

**Последствия.** Бот работает при закрытом Obsidian и на машине без него
(например, на NAS с Syncthing). Ограничения: поиск без индекса Obsidian
(алиасы, теги, ссылки не учитываются), открытое окно Obsidian видит изменения
только после обновления, плагины при записи не выполняются. REST-режим
остаётся по умолчанию, поэтому существующие настройки продолжают работать
без изменений.

## ADR-27: Реестр команд вместо ручного промпта

**Контекст.** Список команд был продублирован: в тексте промпта и отдельно в
схемах инструментов. Добавление команды требовало правок в двух местах, а
расхождения между ними никто не ловил.

**Решение.** `app/actions.py` — единственный источник правды: `Action(name,
title, hint, description, parameters, writes)`. Из реестра собираются схемы
инструментов (`tools()`), блок промпта (`prompt_block()`) и список команд,
которые меняют заметки (`write_actions()`). Новая команда — одна запись в
реестре плюс обработчик в `Agent`; промпт и схемы обновляются сами.

**Последствия.** Добавление команды — два места, а не четыре, и они не могут
разойтись. Ограничение: порядок команд в промпте совпадает с порядком в
реестре, поэтому важные команды стоит держать выше.

## ADR-28: Модель всегда выбирает действие и всегда перерабатывает текст

**Контекст.** Кнопки задавали команду напрямую и экономили запрос, но текст
попадал в заметку как есть. Пользователь попросил, чтобы модель всегда сама
определяла действие и всегда думала над формулировками — в том числе при
дописывании.

**Решение.** Два правила.
1. Свободный текст всегда разбирает модель: она выбирает команду из реестра;
   если ни одна не подходит — вызывает `clarify`, бот показывает вопрос и
   кнопки действий.
2. Любая запись проходит через `compose_note` / `compose_append` /
   `compose_section`: модель переписывает сообщение под заметку (заголовок,
   структура, формат раздела), учитывая уже написанное. Кнопки задают только
   команду — текст всё равно композируется. Если модель недоступна, запись
   не выполняется: пользователь видит ошибку.

**Последствия.** Заметки не содержат разговорных обрывков и копий сообщений.
Цена: +1 запрос к модели на каждую запись через кнопки, и запись зависит от
доступности модели (dry-run и подтверждение сохраняются).

## ADR-29: Шаблоны заметок — файлы в vault, плейсхолдеры подставляет бот

**Контекст.** Новые заметки создавались свободной структурой: модель сама
придумывала разделы. Пользователю нужны повторяемые заметки (встречи,
дневник, проект) с одинаковым frontmatter и набором разделов, редактируемыми
без участия разработчика.

**Решение.** Шаблон — обычная `.md`-заметка в папке `AGENT_TEMPLATE_FOLDER`
(по умолчанию `Templates`), только верхний уровень. В кнопочном сценарии
«Новая заметка» бот показывает до трёх шаблонов кнопками плюс «Без шаблона»;
в свободном диалоге модель вызывает `list_templates` и читает выбранный через
`read_note`. Текст шаблона передаётся модели с требованием сохранить разделы и
их порядок. Плейсхолдеры `{{title}}`, `{{date}}`, `{{time}}` подставляет бот
после ответа модели; неизвестные `{{...}}` не трогаются. Папка `templates/`
в репозитории не считается источником шаблонов: бот читает только vault
(см. ADR-31). Автоматический выбор шаблона по смыслу отклонён: он молча
меняет структуру заметки.

**Последствия.** Шаблоны редактируются в Obsidian и работают в REST- и
файловом режимах. Список шаблонов читается при старте (кнопка создания не
ждёт сеть): новый файл появляется после перезапуска, изменения в уже известном
шаблоне применяются при выборе. Гарантии сохранения разделов нет — модель может
переименовать заголовок; превью до записи это показывает. Шаблоны длиннее
лимита чтения обрезаются; вложенные папки шаблонов не поддерживаются.

## ADR-30: «Мой стиль» — заметка-описание, а не автообучение по заметкам

**Контекст.** Нужно, чтобы новые заметки были написаны в привычном стиле:
тон, длина абзацев, оформление. Можно передавать модели примеры существующих
заметок или отдельное описание стиля.

**Решение.** Стиль — необязательная заметка `AGENT_STYLE_NOTE` (путь в vault).
Она читается один раз при старте, обрезается до 4000 символов и добавляется в
системный промпт и в промпты `compose_note` / `compose_append` /
`compose_section`. При дописывании приоритет у стиля самой заметки. Вариант
«несколько последних заметок как примеры» отклонён: содержимое непредсказуемо,
расходует токены и может противоречить само себе. Изменения стиля применяются
после перезапуска.

**Последствия.** Пользователь явно контролирует стиль и может менять его без
кода. Ограничения: нужна отдельная заметка, стиль кэшируется на время работы,
а слишком большой текст обрезается. В лог попадают только путь и длина, не
содержимое. Заметка стиля не попадает в список шаблонов, даже если лежит в
папке `Templates`.

## ADR-31: Адаптированные шаблоны — копии без Templater, папка-эталон вне git

**Контекст.** В рабочем хранилище уже есть шаблоны (`!00 Шаблон`, `Книга`,
`Дневник  {{date}}`, `Стандартная заметка`, `Gtd week review`), но они
написаны под плагин Templater: `<%* ... %>`, `tp.file.rename`,
`tp.date.now("DD.MM.YY")`. Бот исполняет только собственный рендер
`{{title}}`/`{{date}}`/`{{time}}`, JavaScript шаблона не выполняется. Дать
боту эти файлы как есть — значит отдать модели текст с кодом и вставками
Templater. Шаблоны при этом личные: в них карта хранилища, структура карточки
человека, правила стиля.

**Решение.** В репозитории появилась папка `templates/` с адаптированными
копиями: JavaScript вырезан, даты заменены плейсхолдерами, структура разделов
и порядок frontmatter сохранены. Папка эталонная: бот читает шаблоны только из
`AGENT_TEMPLATE_FOLDER` в хранилище, а копии переносятся в vault вручную
(в тестовом хранилище уже лежат). Сама `templates/` внесена в `.gitignore`,
потому что содержит личные правила и структуру заметок. Оригиналы в рабочем
хранилище не перезаписываются: их использует Templater.

**Последствия.** Шаблоны можно версионировать у себя и переносить между
машинами, но репозиторий их не содержит — после клонирования папки нет, это
ожидаемо. Правка шаблона — это два шага: файл в `templates/` и копия в vault.
Ограничения Templater (номер недели GTD, переименование файла дневника) в
бот-версиях потеряны; они перечислены в
[07_templates_style.md](07_templates_style.md).

## ADR-32: Формат даты и времени в плейсхолдерах — синтаксис Templater

**Контекст.** `{{date}}` давал только `ГГГГ-ММ-ДД`, а в хранилище приняты
`ДД.ММ.ГГГГ` (дневник) и `ДД.ММ.ГГГГ` с номером недели в GTD. Если оставить
только ISO, адаптированные шаблоны выглядят чужеродно, а пользователь не может
задать свой формат без правки кода.

**Решение.** Плейсхолдер принимает формат: `{{date:DD.MM.YY}}`,
`{{time:HH:mm:ss}}`. Токены — `YYYY`, `YY`, `MM`, `M`, `DD`, `D`, `HH`, `mm`,
`ss` (как в Templater/moment); подстановка детерминированная, через словарь
значений из `datetime`, без `strftime`-форматов, чтобы поведение не зависело
от платформы. Пустой формат `{{date:}}` даёт значение по умолчанию.
Неизвестные токены остаются текстом, неизвестные плейсхолдеры по-прежнему не
трогаются. Отклонены `strftime`-форматы (`{{date:%d.%m.%y}}`) — пользователь
пишет шаблоны в привычном ему синтаксисе Obsidian.

**Последствия.** Шаблоны можно адаптировать без потери принятых форматов дат.
Формат остаётся текстом шаблона, поэтому ошибка в токене видна в превью, а не
ломает бота. Номер недели и диапазон дат по-прежнему не вычисляются.

## ADR-33: Связи — раздел «Связи» любого уровня, имя или путь в ссылке

**Контекст.** FR-05 требует добавлять ссылки в раздел `## Связи` в конце
заметки. В хранилище пользователя принят `###### Связи` (шестой уровень,
чтобы не попадать в оглавление) и закрывающий `---`. Если бот создаст второй
раздел `## Связи`, в заметке окажутся два блока связей; если переименует
существующий — сломает оформление. Отдельный вопрос — имена: в хранилище есть
`Projects/Индекс.md` и `Notes/Индекс.md`, и ссылка `[[Индекс]]` открывает
случайную из них.

**Решение.** `add_links` ищет раздел по заголовку «Связи» любого уровня
(сравнение без учёта регистра), дополняет последний найденный блок и сохраняет
закрывающий `---` после списка; новый раздел создаётся как `## Связи` только
если блока нет. Ссылка строится по имени, если имя уникально, и по пути без
`.md` (`[[Notes/Индекс]]`), если такое имя есть в нескольких папках. Алиасы и
якоря при разборе существующих ссылок отбрасываются, поэтому `[[Идеи|мысли]]`
считается ссылкой на «Идеи». Inline-ссылки в авторский текст не вставляются —
только раздел связей.

**Последствия.** Оформление заметок не меняется, дублей блоков не появляется,
повторная простановка идемпотентна. Цена: если пользователь сам переименует
заголовок «Связи» во что-то другое, бот создаст новый раздел; ссылки через
путь перестают работать при переносе заметки в другую папку.

## ADR-34: Отбор связей — модель для одной заметки, правила для всего хранилища

**Контекст.** FR-05 говорит, что кандидатов выбирает LLM. Для массовой
операции (FR-06) это означало бы отдельный запрос к модели на каждую заметку:
300 заметок — 300 запросов, минуты ожидания, расход лимитов и риск, что
модель выберет связи по-разному в соседних заметках.

**Решение.** Для одной заметки (`create`, `append`, `section`, `add_links`)
кандидаты собираются из упоминаний названий и полнотекстового поиска
(он находит совпадения по тексту, алиасам и тегам), а окончательный выбор
делает модель — до `AGENT_LINK_LIMIT`; выбрать можно только из предложенных
путей, неизвестные строки отбрасываются. Если модель недоступна, берутся
первые упоминания (до трёх). Для массовой операции модель не используется:
связи ставятся по точным упоминаниям названий, причём только с заглавной
буквы или цифры (`strict`), чтобы слово «человек» не превращалось в ссылку
на заметку «Человек». Шаблоны и заметка стиля исключаются из скана: их текст
копируется в новые заметки.

**Последствия.** Массовая операция быстрая, предсказуемая и бесплатная, но
пропускает упоминания в нижнем регистре и без точного совпадения названия:
такие связи ставятся по одной заметке через модель. План всегда показывается
до записи с примерами, а подтверждение обязательно в `auto` и `always` —
именно там пользователь отсекает ложные срабатывания. Ошибки по отдельным
заметкам не прерывают операцию и попадают в отчёт.

## ADR-35: Папку предлагает бот — кнопками, из заголовка и из текста

**Контекст.** На ручном прогоне карточка человека создавалась так: модель
предложила заголовок `Люди/101 Александр Шевчук`, бот показал «Куда
сохранить?» с кнопками «Inbox / Автоопределение / Другая папка». Подсказок
папок не было, папка из заголовка потерялась (слэш при слагификации стал
пробелом), а ответ «Создай папку люди и добавь туда» ушёл в модель, и та
повторила то же предложение. Пользователь не мог ни увидеть вариант «Люди»,
ни создать папку одним действием.

**Решение.** Папка стала полноценной частью предложения:
- у команды `create_note` появился параметр `folder` — модель передаёт папку
  отдельно от заголовка;
- если папка всё же попала в заголовок, первый сегмент отделяется
  (`Люди/101 Александр` → папка «Люди», заголовок «101 Александр»), когда он
  совпадает с существующей папкой или выглядит как одно слово без цифр;
  «Q3/Q4 итоги» не разрезается;
- при создании бот сразу показывает до трёх подсказанных папок кнопками
  (модель, а при её недоступности — совпадение названия папки с текстом),
  затем Inbox, «Автоопределение», «Другая папка», «Отмена»;
- на шаге выбора папки любой текст считается папкой и разбирается:
  служебные слова («создай», «папку», «добавь», «туда») отбрасываются,
  существующая папка возвращается в своём написании, обычная фраза папкой
  не считается и приводит к переспросу;
- если папки нет, бот спрашивает «Создать её?» и создаёт только после
  подтверждения (FR-04.4), как и раньше.

**Последствия.** Пользователь видит варианты папок до нажатия и может создать
новую одним ответом. Цена: при создании заметки бот делает дополнительный
запрос к модели для подсказки папок, если папка не названа в заголовке или
пользователем; подсказка не гарантирует точного попадания, но папка всегда
меняема кнопкой, а запись по-прежнему подтверждается. Текст на шаге папки
больше нельзя использовать как новый запрос к модели — это осознанный
компромисс: состояние «ждём папку» должно быть однозначным.

## ADR-36: Поиск по тексту очищает запрос от команд и кавычек

**Контекст.** В сценарии «Найти» пользователь отправил `Найди "код заморожен"`,
хотя в заметке есть строка «Код заморожен». Поиск искал точную подстроку всего
сообщения: кавычки и слово «Найди» в тексте заметки отсутствуют, поэтому выдача
была пустой. Имена файлов при этом искались отдельно и нормализовались, а текст
заметок — нет.

**Решение.** `app/search.py` очищает запрос одинаково для имён и текста:
нижний регистр, «ё» → «е», пунктуация в пробелы, служебные слова и глаголы
поиска («найди», «покажи», «заметка», «текст», предлоги) отбрасываются.
Совпадение фразы целиком даёт 1.0, всех слов в любом порядке — 0.9; слова
короче двух символов не учитываются. Файловый режим читает заметки и
ранжирует совпадения по этой оценке, REST-режим отправляет в `/search/simple/`
очищенный запрос. Имена файлов по-прежнему идут раньше текста.

**Последствия.** Запросы вида «Найди "код заморожен"», «код заморожен» и
«заморожен» находят заметку по содержимому, порядок слов не важен. Цена:
поиск остаётся полнотекстовым, без морфологии — «заморозка» не найдёт
«заморожен», а лишнее слово в запросе требует своего присутствия в заметке.
Файловый режим читает все заметки до лимита, чтобы отсортировать совпадения.

## ADR-37: Разделы, папки, копирование, перенос и удаление заметок

**Контекст.** Бот умел создавать и править заметки, но не умел добавить новый
раздел, создать или переименовать папку, скопировать, перенести или удалить
заметку. Для этих операций нужны и инструменты модели, и безопасный путь
выполнения: подтверждение, dry-run, защита от перезаписи и выход за пределы
хранилища.

**Решение.**
- `app/notes.py`: `create_section()` добавляет раздел в конец заметки и не
  допускает дубль заголовка; `validate_folder()` проверяет путь папки;
  `destination_path()` принимает полный путь с `.md` или папку (тогда имя файла
  сохраняется).
- `ObsidianBackend`: новые методы `list_folders`, `create_folder`,
  `rename_folder`, `delete_folder`, `delete_note`, `copy_note`, `move_note`.
- `VaultClient`: папки и файлы переименовываются атомарно; удаление перемещает
  объект в `.trash` с сохранением относительного пути; копирование —
  `shutil.copy2`; перемещение — `Path.rename`.
- `ObsidianClient`: `MOVE`/`COPY`/`DELETE` REST API; папка создаётся скрытым
  файлом `.keep`; переименование и удаление папки выполняются переносом или
  удалением всех её заметок, потому что API не умеет работать с каталогами.
- В `app/actions.py` добавлены инструменты `create_section`, `create_folder`,
  `rename_folder`, `delete_folder`, `move_note`, `copy_note`, `delete_note`.
  Все они `writes=True`, поэтому проходят через общее подтверждение.
- В режиме `auto` новые операции подтверждаются всегда; в `never` выполняются
  сразу; dry-run возвращает «не выполнено» и ничего не меняет.
- Пути проверяются до записи: выход за vault, `.`/`..`, служебные папки с
  точкой, перезапись существующего файла и совпадение старого и нового пути
  запрещены.

**Последствия.** Удаление обратимо: в файловом режиме объект лежит в `.trash`,
в REST-режиме Obsidian отправляет его в свою корзину. В REST-режиме после
переименования или удаления папки пустой старый каталог может остаться, а
`.keep` виден только в файловой системе, не в списке заметок. Раздел всегда
добавляется в конец заметки; удаление и перестановка разделов не входят в этот
этап.
