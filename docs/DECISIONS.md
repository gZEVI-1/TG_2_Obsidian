# Журнал архитектурных решений (ADR-lite)

Короткие записи о ключевых решениях: контекст, решение, последствия.
Нумерация сквозная, записи не удаляются — устаревшие помечаются как заменённые.

## ADR-01: Документирование каждого этапа в `docs/`

**Контекст.** Проект ведётся поэтапно, между этапами возможны паузы. Нужно
понимать состояние проекта, не читая код.

**Решение.** Один md-файл на этап (`docs/NN_<название>.md`) с обязательными
разделами, оглавление в `docs/README.md`, решения — в этом файле.

**Последствия.** Документация обновляется в том же этапе, где меняется код.
Стоимость: немного времени на каждый этап. Выгода: вход в проект и откат без
чтения кода.

## ADR-02: Один OpenAI-совместимый слой доступа к LLM

**Контекст.** Нужен бесплатный или очень дешёвый внешний провайдер с
возможностью быстро менять модель и провайдера.

**Решение.** Все обращения к LLM идут через один HTTP-клиент к
OpenAI-совместимому эндпоинту. Провайдер, базовый URL, ключ и модель задаются
только переменными `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.

**Последствия.** Смена модели — правка `.env` и перезапуск, без изменений кода.
Ограничение: доступны только провайдеры с OpenAI-совместимым API. Качество
tool-calling зависит от выбранной модели — проверяется на Этапе 4.

## ADR-03: Кроссплатформенность (Windows → NAS)

**Контекст.** Сейчас запуск на Windows-ПК, позже перенос на NAS (Linux).

**Решение.** Никаких Windows-специфичных вызовов и путей: `pathlib`, работа с
кодировками через явный UTF-8, конфигурация только через переменные окружения.

**Последствия.** Перенос сводится к установке Python и копированию проекта с
`.env`. Контейнеризация (Docker) отложена до этапа переноса.

## ADR-04: RAG откладывается

**Контекст.** Задача — создавать заметки и ставить связи. Семантический поиск
требует эмбеддингов, векторной БД и инкрементальной индексации.

**Решение.** На первых этапах связи ставятся по именам файлов, алиасам и тегам.
Эмбеддинги и ChromaDB — отдельный опциональный Этап 8.

**Последствия.** Меньше зависимостей и точек отказа. Ограничение: поиск «по
смыслу» появится позже; возможен переход на Python 3.12 в venv из-за
совместимости пакетов.

## ADR-05: Тестовый vault и dry-run по умолчанию

**Контекст.** Запись в Obsidian необратима, ошибка агента может испортить
рабочее хранилище.

**Решение.** Разработка и проверки — только на тестовом vault.
`OBSIDIAN_DRY_RUN=true` по умолчанию: операции записи логируются, но не
выполняются. Рабочий vault подключается последним, по явному разрешению.

**Последствия.** Часть проверок требует двух прогонов (dry-run и реальная
запись). Зато агент нельзя случайно направить в рабочее хранилище.

## ADR-06: Конфигурация без pydantic

**Контекст.** На Этапе 1 нужны плоские настройки из `.env`.

**Решение.** `dataclass` + `os.environ` + `python-dotenv`, ручная валидация
`LOG_LEVEL` и булевых значений.

**Последствия.** Одна зависимость вместо трёх, прозрачное поведение. Если
появятся вложенные структуры или списки, вернёмся к `pydantic-settings` по
согласованию.

## ADR-07: Корень проекта — клон репозитория `TG_2_Obsidian`

**Контекст.** Рабочая папка `E:\FOLDER\TG-OBS` не является репозиторием, а код
должен версионироваться. Пользователь клонировал в неё свой репозиторий
`gZEVI-1/TG_2_Obsidian` (пустой, только `README` и `LICENSE`).

**Решение.** Корень проекта — `E:\FOLDER\TG-OBS\TG_2_Obsidian`. Код, `docs/`,
`requirements.txt`, `.env.example` лежат в корне этого репозитория. Собственный
`.gitignore` не добавлялся: в репозитории уже есть стандартный Python-шаблон,
исключающий `.env` и `.venv/`. Ключ Obsidian в `.env` приведён к
`OBSIDIAN_API_KEY` (было `Obs_rest_api`). Тестовое хранилище
`TG-OBS-vault-test` остаётся отдельной папкой рядом и в git не попадает.

**Последствия.** Один репозиторий, один `.venv`, коммиты из корня проекта.
Секреты по-прежнему только в `.env` вне контроля версий.

## ADR-08: Имена переменных окружения в едином стиле

**Контекст.** В `.env` пользователя ключ Obsidian назывался `Obs_rest_api`.

**Решение.** Все переменные — в `UPPER_SNAKE_CASE` с префиксом подсистемы:
`TELEGRAM_*`, `LLM_*`, `OBSIDIAN_*`.

**Последствия.** Совпадение имён с `.env.example` и кодом, меньше опечаток.
Переименование выполнено один раз на Этапе 1; резервная копия старого файла
лежит вне репозитория.

## ADR-09: Long polling вместо webhook

**Контекст.** Бот запускается на домашнем ПК за NAT: нет публичного адреса,
нет домена и сертификата для входящих HTTPS-запросов Telegram.

**Решение.** `Dispatcher.start_polling()`. Webhook не используется.
Перед polling вызывается `delete_webhook(drop_pending_updates=True)`, чтобы
старый webhook не блокировал получение обновлений.

**Последствия.** Ноль настроек на стороне сети, запуск одной командой.
Ограничение: бот работает только пока запущен процесс; на NAS при переносе
вернёмся к вопросу (возможен webhook + reverse proxy).

## ADR-10: Запись в vault только без молчаливой перезаписи

**Контекст.** Агент будет создавать заметки по тексту пользователя. Имя,
предложенное LLM, легко совпадёт с существующей заметкой; `PUT` в Local REST API
перезаписывает файл без вопросов.

**Решение.** `ObsidianClient.write_note()` по умолчанию проверяет существование
файла и при совпадении бросает `ObsidianError`. Перезапись — только явным
`overwrite=True`. В dry-run клиент не отправляет изменяющих запросов вообще.

**Последствия.** Потеря заметки из-за совпадения имени исключена на уровне
клиента, а не «внимательности промпта». Цена: лишний `GET` перед записью.

## ADR-11: `aiohttp` как HTTP-клиент

**Контекст.** Нужны запросы к Obsidian REST API из асинхронного бота.
`aiohttp` уже установлен как зависимость aiogram.

**Решение.** Использовать `aiohttp` напрямую: одна `ClientSession` на клиент,
таймаут 10 секунд, `Authorization: Bearer`.

**Последствия.** Нет блокировки event loop и лишних зависимостей. Ограничение:
`requests` в проекте не используется, синхронные утилиты писать не будем.
