# Этап 4: LLM-клиент (OpenAI-совместимый API)

## Этап

Этап 4 — клиент OpenAI-совместимого API: провайдер OpenRouter, проверка ответа
и поддержки tool-calls, ответ бота через модель вместо эха.

## Цель

Подключить модель через один OpenAI-совместимый слой и убедиться, что она
отвечает по-русски и умеет вызывать инструменты. От tool-calls зависит Этап 5,
поэтому это проверяется запросом, а не предположением.

## Что сделано

- `app/llm.py` (новый):
  - `LLMError` — единый тип ошибок клиента;
  - `ToolCall` — запрос модели на вызов инструмента (`id`, `name`,
    `arguments` — JSON-строка);
  - `LLMResponse` — текст, `tool_calls`, имя модели, `finish_reason`;
  - `LLMClient` — одна `ClientSession` на клиент, `Authorization: Bearer`,
    таймаут 60 секунд, `POST {LLM_BASE_URL}/chat/completions`;
  - `chat(messages, tools=None, max_tokens=800)` — необязательный список
    инструментов, разбор `choices[0].message`, текст обрезается по краям;
  - контекстный менеджер (`async with`) и `close()`;
  - ошибки: не-200 → `LLMError` с кодом и обрезанным телом ответа, не-JSON и
    пустой `choices` — тоже `LLMError`;
  - пустые `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` → `LLMError`
    при создании клиента.
- `app/__main__.py`:
  - флаг `--check-llm` (взаимоисключающий с `--check-config` и
    `--check-obsidian`): первый запрос — обычный текстовый ответ, второй —
    запрос с dummy-инструментом `get_weather`, чтобы увидеть, вернёт ли модель
    `tool_calls`;
  - `LLMError` и `aiohttp.ClientError` → понятное сообщение в лог, exit code 2;
  - `run_bot()` обёрнут в обработку `LLMError`: если LLM не настроена, бот
    не стартует с трейсбеком, а пишет причину.
- `app/bot.py`:
  - обработчик `echo_text` заменён на `answer_text(message, llm)`: системный
    промпт «отвечай по-русски, кратко и по делу», ответ модели уходит в чат;
  - при `LLMError` пользователь получает «Не удалось получить ответ от модели.
    Попробуйте позже.», подробность — в лог;
  - `run_bot()` создаёт `LLMClient` и передаёт его в
    `start_polling(bot, llm=llm)` (workflow data), закрывает клиент в `finally`;
  - тексты `/start` и `/help` обновлены: эха больше нет.
- `requirements.txt` — без изменений: `aiohttp` уже объявлен на Этапе 3.
- `.env` — `LLM_MODEL` переключён с `google/gemma-4-31b-it:free` на
  `nvidia/nemotron-3-ultra-550b-a55b:free` (причина — ниже, в «Принятые
  решения»). Значения `LLM_BASE_URL` и `LLM_API_KEY` задал пользователь.

## Внешние действия

Выполнено пользователем:

1. Получен ключ OpenRouter (`openrouter.ai` → Settings → Keys → Create Key).
2. В `.env` заполнены `LLM_BASE_URL=https://openrouter.ai/api/v1`,
   `LLM_API_KEY`, `LLM_MODEL`. Ключ в переписку не передавался.
3. Проверка ключа и модели выполнена командой `--check-llm` (см. ниже).

## Принятые решения

- **OpenRouter как провайдер этапа** (ADR-12). На этапе разработки нужен
  нулевой бюджет: у OpenRouter есть модели с суффиксом `:free`, API
  OpenAI-совместимый, смена модели — одна строка в `.env`.
- **Модель заменена на `nvidia/nemotron-3-ultra-550b-a55b:free`.**
  У `google/gemma-4-31b-it:free` три попытки подряд (интервал 25 секунд)
  вернули `HTTP 429` с текстом «temporarily rate-limited upstream» — это
  ограничение не нашего ключа, а общего пула Google AI Studio. Nemotron
  ответил за 3–4 секунды, по-русски корректно, tool-calls отработали.
  Модель — это значение в `.env`, откат к gemma возможен в любой момент.
- **Tool-calls проверяются реальным запросом** с dummy-инструментом
  `get_weather`, а не «на глаз» по ответу модели: если модель не умеет
  инструменты, Этап 5 придётся делать на другой модели, и лучше узнать это
  сейчас.
- **Без истории диалога** (ADR-13): один запрос — один ответ. История и цикл
  инструментов появятся вместе с агентом на Этапе 5, иначе этот код пришлось
  бы переписывать дважды.
- **`max_tokens=800`.** Ответ гарантированно короче лимита Telegram
  (4096 символов), поэтому нарезка сообщений пока не нужна.
- **`temperature` не передаётся.** Не все провайдеры её принимают, а на этом
  этапе важнее совместимость, чем управление вариативностью.
- **Без ретраев.** `429` на free-тарифе — штатная ситуация, но слепые ретраи
  жгут дневной лимит и растягивают ответ. Осмысленные повторы — Этап 9.

## Как проверить

```powershell
cd E:\FOLDER\TG-OBS\TG_2_Obsidian
.\.venv\Scripts\python.exe -m app --check-llm     # 2 запроса к модели
```

Ожидается (реальный вывод этапа):

```
INFO app: Модель ответила (nvidia/nemotron-3-ultra-550b-a55b:free): Obsidian — это мощный редактор заметок...
INFO app: Tool-calls поддерживаются: get_weather({"city":"Москва"})
```

Если вторая строка — предупреждение «Модель не вызвала инструмент», значит
модель не умеет tool-calls: менять `LLM_MODEL`, а не код.

Затем — бот:

```powershell
.\.venv\Scripts\python.exe -m app
```

Ожидается: в логе `Бот @<username> запущен`, в Telegram `/start` и `/help`
отвечают, любой текст получает ответ модели, фото/стикер — «Пока я понимаю
только текст». При недоступной модели — сообщение об ошибке вместо зависания.

Проверки, выполненные на этапе: `--check-config`, `--check-obsidian`
(dry-run), `--check-llm` (текст + tool-calls), вызов обработчика
`answer_text()` с поддельным сообщением — ответ получен без Telegram.

## Риски и откат

- Риск: дневной лимит free-тарифа — 50 запросов в сутки при покупке кредитов
  менее $10, иначе 1000; 20 запросов в минуту. Одна проверка `--check-llm` —
  два запроса. При исчерпании ответ 429 до следующих суток (UTC).
- Риск: бесплатная модель исчезает из каталога (`404`) или перегружена
  (`429`). Лечится сменой `LLM_MODEL`, код не меняется.
- Риск: провайдеры бесплатных моделей могут обучаться на промптах. Поэтому
  работаем только с тестовым vault и не отправляем личные заметки, пока
  вопрос приватности не решён (Этап 9–10).
- Риск: ответ длиннее лимита Telegram. При `max_tokens=800` недостижимо; если
  лимит поднимать — понадобится нарезка сообщений.
- Откат: удалить `app/llm.py`, вернуть в `app/bot.py` обработчик-эхо, убрать
  флаг `--check-llm`, вернуть прежний `LLM_MODEL`. `.env` в git не попадает,
  секреты при откате не затрагиваются.
