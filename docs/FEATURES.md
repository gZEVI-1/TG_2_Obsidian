# Функциональные требования: заметки, расположение и связи

Документ фиксирует целевое поведение Этапов 5–7: работа с заметками,
автоматическое расположение внутри хранилища, связи и обработка ошибок.
Требования дополняют [00_requirements.md](00_requirements.md), технические
решения — в [DECISIONS.md](DECISIONS.md) (ADR-15…ADR-20).

## 1. Общие правила

- **Ничего не додумывать.** Если название заметки, раздел, папка или связь
  неоднозначны, агент задаёт вопрос. Молчаливый выбор «наиболее вероятного»
  варианта запрещён.
- **Любая запись — только через `ObsidianClient`.** Прямых запросов к файлам
  vault нет.
- **Нет молчаливой перезаписи и удаления.** Существующая заметка не
  заменяется целиком; изменение — это добавление или правка выбранного
  раздела (FR-03).
- **Dry-run сохраняется.** При `OBSIDIAN_DRY_RUN=true` агент показывает, что
  сделал бы, но не отправляет изменяющих запросов.
- **Ошибка не равна успеху.** Если API вернул ошибку или запись не
  подтверждена, пользователь видит сообщение, а операция не считается
  выполненной (FR-08).
- **Одна глобальная настройка подтверждений.** `AGENT_CONFIRMATION`
  управляет всеми операциями (FR-07); отдельные переключатели не вводятся
  без необходимости.

## 2. Термины

- **Заметка** — Markdown-файл в vault Obsidian.
- **Контекст** — текст текущего запроса и история диалога, по которым
  определяется, о какой заметке или папке идёт речь.
- **Связь** — ссылка Obsidian вида `[[Имя заметки]]` на существующую заметку.
- **Неоднозначность** — несколько подходящих заметок/разделов/папок, низкая
  уверенность выбора или противоречивые указания пользователя.
- **Подтверждение** — явный ответ пользователя «да» на вопрос бота перед
  записью.

## 3. FR-01: Создание новой заметки

**Сценарий.** Пользователь просит сохранить мысль, текст или итог разговора
в новую заметку.

**Поведение.**

1. Агент определяет заголовок и содержание. Заголовок берётся из слов
   пользователя; если его нет — предлагается вариант и запрашивается
   подтверждение.
2. Проверяется, нет ли заметки с таким путём. При совпадении создание
   останавливается: предлагается дописать в существующую (FR-02) или выбрать
   другое имя.
3. Папка выбирается по FR-04 (кнопки «Inbox» / «Автоопределение»).
4. Заметка создаётся через `write_note(..., overwrite=False)`.
5. Пользователь получает путь заметки и, если включена автолинковка,
   результат FR-05.

**Критерии приёмки.**

- Новая заметка появляется по выбранному пути, содержимое читается.
- Существующая заметка не перезаписывается.
- При `OBSIDIAN_DRY_RUN=true` в vault ничего не создаётся, в логе — план.
- При неоднозначном заголовке или папке бот задаёт вопрос.

## 4. FR-02: Добавление в существующую заметку

**Сценарий.** Пользователь хочет дописать текст в уже существующую заметку,
но не помнит точное имя.

**Поведение.**

1. Выполняется поиск по контексту (FR-09). Пользователю показываются до
   `AGENT_SEARCH_LIMIT` кандидатов с фрагментами совпадений.
2. Если найден один явный кандидат — бот предлагает его. Если кандидатов
   несколько или уверенность низкая — задаёт вопрос с кнопками.
3. Если ничего не найдено — предлагает создать новую заметку (FR-01), а не
   создаёт её молча.
4. После выбора заметки текст добавляется в конец отдельным блоком; при
   указании раздела — по FR-03.
5. Перед записью показывается, что именно будет добавлено, если этого требует
   `AGENT_CONFIRMATION`.

**Критерии приёмки.**

- Изменена только выбранная заметка; остальные не затрагиваются.
- Существующий текст, frontmatter и ссылки сохранены.
- Повторное добавление того же текста не создаёт скрытых дублей: агент
  предупреждает о совпадении.
- При неоднозначности запись не выполняется до ответа пользователя.

## 5. FR-03: Изменение существующей заметки

**Сценарий.** Пользователь просит изменить формулировку, дополнить или
поправить конкретный раздел заметки.

**Поведение.**

1. Заметка находится по FR-09 и показывается пользователю.
2. Раздел определяется по заголовку Markdown. Если подходящий раздел один —
   предлагается он; если несколько или ни одного — бот спрашивает.
3. Изменение выполняется по схеме read-modify-write:
   - прочитать заметку целиком;
   - сохранить frontmatter, остальные разделы и существующие ссылки;
   - заменить содержимое выбранного раздела или дописать в его конец;
   - записать файл.
4. Перед записью показывается diff или краткое описание изменения, если
   `AGENT_CONFIRMATION` требует подтверждения.
5. Полная замена содержимого в рамках FR-03 не выполняется. Если она
   понадобится, это отдельная операция с отдельным подтверждением и отдельным
   требованием.

**Критерии приёмки.**

- Меняется только выбранный раздел; frontmatter и остальные разделы
  сохраняются.
- При неоднозначном разделе запись не выполняется.
- В dry-run файл не меняется, показывается план.
- После записи заметка остаётся валидным Markdown и читается Obsidian.

## 6. FR-04: Автоматическое расположение заметки

**Сценарий.** При создании заметки нужно решить, в какую папку vault её
положить.

**Поведение.**

1. После определения заметки бот показывает inline-кнопки:
   **«Inbox»** и **«Автоопределение»** (при необходимости — «Другая папка»).
2. **Inbox** — папка `AGENT_DEFAULT_FOLDER` (по умолчанию `Inbox`). Если её
   нет, она создаётся; это единственное создание папки без отдельного вопроса.
3. **Автоопределение** — агент получает список существующих папок и контекст
   заметки, выбирает подходящую папку. При высокой уверенности предлагает её;
   при неоднозначности показывает 2–3 варианта и Inbox.
4. Новая папка (кроме Inbox) создаётся только после подтверждения.
5. Путь проверяется: запрещённые символы, `..`, пустые сегменты, слишком
   длинные имена; кириллица и вложенность поддерживаются.
6. При `AGENT_AUTO_FOLDER=false` кнопка «Автоопределение» не показывается:
   доступны Inbox и «Другая папка».
7. При совпадении пути — FR-01, шаг 2.

**Критерии приёмки.**

- Пользователь всегда видит, в какую папку попадёт заметка, до записи.
- Без подтверждения не создаются новые папки, кроме Inbox.
- Автоопределение не выбирает папку, если уверенность низкая: задаёт вопрос.
- Путь корректен для Local REST API и Obsidian.

## 7. FR-05: Автопростановка связей при создании и изменении

**Сценарий.** После создания или изменения заметки нужно связать её с уже
существующими заметками.

**Поведение.**

1. Если `AGENT_AUTO_LINK=true`, агент ищет кандидатов по названиям, алиасам,
   тегам и полному тексту; LLM выбирает до `AGENT_LINK_LIMIT` наиболее
   релевантных.
2. Исключаются: сама заметка, уже существующие ссылки, несуществующие
   заметки и дубли.
3. Ссылки добавляются в раздел `## Связи` в конце заметки в виде
   `- [[Имя заметки]]`. Существующий раздел дополняется, а не заменяется.
   Inline-ссылки в авторском тексте по умолчанию не вставляются.
4. Если кандидатов несколько, уверенность низкая или `AGENT_CONFIRMATION`
   требует подтверждения, бот показывает список ссылок и ждёт ответа.
5. При `AGENT_AUTO_LINK=false` автолинковка не выполняется; доступна
   ручная команда.

**Критерии приёмки.**

- Добавлены только ссылки на существующие заметки.
- Нет самоссылок и дублей; существующие ссылки не удалены.
- Авторский текст не изменён, кроме добавления раздела `## Связи`.
- В dry-run ссылки не записываются, показывается план.

## 8. FR-06: Простановка связей во всех заметках

**Сценарий.** Пользователь запускает отдельную операцию «проставить связи во
всех заметках».

**Поведение.**

1. Агент сканирует все `.md` в vault (кроме служебных папок вроде
   `.obsidian` и `.trash`), с ограничением и прогрессом; строит план: какие
   заметки будут изменены и какие ссылки добавятся.
2. Показывается сводка: количество заметок, ссылок, примеры. В
   `AGENT_CONFIRMATION=auto` массовая операция **всегда** требует
   подтверждения; в `always` — тоже; в `never` — выполняется без вопроса.
3. После подтверждения изменения применяются пакетами. Уже существующие
   ссылки пропускаются; повторный запуск идемпотентен.
4. Ошибки по отдельным заметкам не прерывают всю операцию: они собираются и
   показываются в отчёте, успешные изменения сохраняются.
5. В dry-run создаётся только план, vault не меняется.

**Критерии приёмки.**

- До записи пользователь видит план и подтверждает его.
- Нет дублей, самоссылок и ссылок на несуществующие заметки.
- Повторный запуск не добавляет те же ссылки снова.
- Ошибки видны пользователю, а не проглатываются.

## 9. FR-07: Глобальная настройка подтверждений

**Переменная:** `AGENT_CONFIRMATION`.

| Значение | Поведение |
|----------|-----------|
| `auto` (по умолчанию) | Спрашивать только при неоднозначности или высоком риске: несколько кандидатов, низкая уверенность, неясный раздел/папка, создание новой папки, массовая операция, разрушающее изменение. |
| `always` | Спрашивать перед любой записью в vault. |
| `never` | Не спрашивать; выполнять сразу. Опасный режим, использовать осознанно. |

**Правила.**

- В `auto` массовая простановка связей (FR-06) всегда требует подтверждения.
- Если пользователь не ответил или ответ неоднозначен, запись не выполняется.
- Подтверждение запрашивается inline-кнопками; ответ «нет» отменяет операцию
  без изменений.
- Настройка не отменяет dry-run и не разрешает полную перезапись заметки.

**Критерии приёмки.**

- Значение читается из `.env`; неверное значение — понятная ошибка.
- Поведение одинаково для создания, добавления, изменения и связей.
- В `auto` простой однозначный сценарий не требует лишнего вопроса.

## 10. FR-08: Обработка ошибок API и сервера

**Сценарий.** Obsidian, Local REST API, LLM или сеть недоступны либо
возвращают ошибку.

**Классификация и поведение.**

| Ситуация | Действие |
|----------|----------|
| Нет конфигурации / неверный ключ (`401`, `403`) | Сообщить, что проверить в `.env`; не повторять запрос. |
| Заметка не найдена (`404`) | Предложить поиск (FR-09) или создание (FR-01). |
| Конфликт / заметка уже существует (`409` или проверка перед записью) | Не перезаписывать; предложить дописать или выбрать другое имя. |
| Лимит запросов (`429`) | Сообщить о лимите, учесть `Retry-After`, не зацикливать повторы. |
| Ошибка сервера (`5xx`) | Ограниченный повтор для идемпотентных чтений; для записи — сначала проверить состояние. |
| Сеть / таймаут | Понятное сообщение, повтор только там, где это безопасно. |
| Некорректный ответ API | Записать подробность в лог, сообщить пользователю, не считать операцию успешной. |

**Правила.**

- Сообщение пользователю — короткое и с действием («проверьте, что Obsidian
  запущен», «попробуйте позже»), подробности — в лог.
- Секреты не попадают ни в сообщения, ни в лог.
- Запись не считается успешной, пока API не подтвердил её.
- Повторные попытки не должны создавать дубли заметок или ссылок.
- Бот не падает от сетевой ошибки: обработчик отвечает пользователю и
  продолжает работу.

**Критерии приёмки.**

- Сценарии `401`, `404`, `409`, `429`, `5xx`, таймаут и обрыв сети проверены
  на подставных ответах.
- Бот отвечает пользователю и не завершает процесс.
- После ошибки нет частично записанных или дублирующихся заметок.

## 11. FR-09: Поиск заметок по контексту

**Сценарий.** Нужно найти существующую заметку по контексту запроса (словам
и фразам), но без эмбеддингов и RAG.

**Поведение.**

1. Основной способ — полнотекстовый поиск Local REST API
   (`POST /search/simple/?query=...`).
2. Если Search API недоступен — резервный способ: список файлов
   (`GET /vault/`) и чтение кандидатов; количество ограничено.
3. Запрос формируется из ключевых слов пользователя; LLM может выделить
   ключевые фразы.
4. Ранжирование: точное имя/алиас/тег, затем совпадения в содержимом.
5. Возвращается до `AGENT_SEARCH_LIMIT` кандидатов с фрагментами. Если
   ничего не найдено — предложить создание новой заметки.

**Критерии приёмки.**

- Заметка находится по словам из её содержимого, в том числе по-русски.
- При нескольких результатах бот показывает варианты, а не выбирает молча.
- Поиск не изменяет vault.
- RAG (Этап 8) может улучшить поиск, но не отменяет этот сценарий.

## 12. FR-10: Правила связей

- Ссылка создаётся только на существующую заметку.
- Формат — `[[Имя заметки]]`; при неоднозначном имени используется путь.
- Самоссылки, дубли и ссылки на удалённые заметки не создаются.
- Существующие ссылки и разделы не удаляются.
- Связи добавляются в раздел `## Связи`; повторный запуск не дублирует их.
- Обратные ссылки Obsidian строит сам; агент отвечает только за исходящие.

## 13. Настройки

| Переменная | Значения | По умолчанию | Этап |
|------------|----------|--------------|------|
| `AGENT_CONFIRMATION` | `auto`, `always`, `never` | `auto` | 5 |
| `AGENT_DEFAULT_FOLDER` | путь папки | `Inbox` | 5 |
| `AGENT_AUTO_FOLDER` | `true`, `false` | `true` | 5 |
| `AGENT_AUTO_LINK` | `true`, `false` | `true` | 7 |
| `AGENT_SEARCH_LIMIT` | целое, 1–20 | `5` | 5 |
| `AGENT_LINK_LIMIT` | целое, 1–50 | `10` | 7 |

Неверные значения валидируются при загрузке настроек: опечатка должна
проявляться сразу, а не молча подставляться.

## 15. Критерии готовности

- Все сценарии FR-01…FR-10 проверены на тестовом vault.
- Проверены dry-run и реальная запись.
- Проверены ошибки API/сервера и отсутствие дублей после повторов.
- Настройки из раздела 13 читаются и валидируются.
- Документация обновлена в том же этапе, где менялся код (ADR-01).
