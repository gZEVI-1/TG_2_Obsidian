# Этап 11: готовность, лог в файл, резервные копии и доступ

## Этап

Этап 11 — эксплуатация без службы: на текущем ПК хватает ручного запуска, но
нужны проверка готовности, журнал в файле, резервные копии хранилища и защита
доступа к Local REST API. Автозапуск, HTTPS/туннель и перенос — опциональный
этап 12 (инфраструктура готова, [16_ci_docker.md](16_ci_docker.md)).

## Цель

Сделать так, чтобы:

- перед запуском и при разборе проблем одна команда показывала состояние
  хранилища, LLM, RAG, журнала, копий и доступа — без записи в заметки;
- лог не терялся при закрытом окне терминала и не рос без предела;
- хранилище и журнал можно было сохранить одной командой, не копируя секреты;
- было видно, если REST API случайно оказался доступен по сети без TLS.

## Что сделано

- `app/logging_setup.py` — второй обработчик лога: файл с ротацией
  (`RotatingFileHandler`, 2 МБ × 5 файлов, UTF-8). Путь из `LOG_FILE`
  (по умолчанию `state/logs/app.log`, пусто — только консоль). Повторная
  настройка после чтения `.env` заменяет обработчики, а не дублирует строки;
  если файл недоступен — предупреждение в stderr, лог продолжает идти в консоль.
- `app/health.py` — `check_health()` и `python -m app --health`: восемь
  проверок, ничего не пишут в хранилище и не вызывают модель:
  - `хранилище` — `health()` активного бэкенда; в `auto` показываются оба;
  - `LLM` — заглушки/аккаунты/модели (без сетевого запроса);
  - `RAG` — зависимости и наличие индекса;
  - `аудит` — папка `state/audit` создаётся и доступна на запись;
  - `копии` — `BACKUP_DIR` задан и доступен;
  - `доступ` — адрес REST API локальный (`127.0.0.1`, `localhost`, `::1`);
  - `лог` — папка для файла лога доступна на запись;
  - `запись` — `OBSIDIAN_DRY_RUN` (true — предупреждение).
  Критичные ошибки (хранилище, аудит, лог, копии, LLM) дают код возврата 2.
- `app/backup.py` — `python -m app --backup`: zip в `BACKUP_DIR` с папками
  `vault/` и `state/audit/` и файлом `backup-info.txt` (что внутри и чего нет).
  Хранятся последние `BACKUP_KEEP` копий (по умолчанию 7).
- `app/config.py` — новые настройки `LOG_FILE`, `BACKUP_DIR`, `BACKUP_KEEP`
  (1–100), свойства `log_path` и `backup_path`; проверка `is_local_url()`
  и предупреждение при старте, если `OBSIDIAN_BASE_URL` указывает не на этот
  компьютер (REST без TLS виден по сети).
- `app/__main__.py` — команды `--health` и `--backup`, лог настраивается
  на файл после чтения `.env`.
- `tests/test_backup.py` (6 тестов) и `tests/test_health.py` (7 тестов).

## Внешние действия

1. Задать `BACKUP_DIR` в `.env` — папку вне хранилища, например
   `E:\FOLDER\TG-OBS\backups`. Без неё `--backup` честно откажется, а
   `--health` покажет предупреждение.
2. Копии делает сам бот, пока запущен: при старте, если последняя старше
   `BACKUP_EVERY_HOURS`, и далее проверка раз в час (этап 14 —
   [15_auto_backup.md](15_auto_backup.md)). `--backup` остаётся для копии
   «прямо сейчас».
3. Obsidian держать с `HTTP Server` на `127.0.0.1:27123`; порт в роутере не
   открывать. Для NAS/VPS есть Docker, systemd и HTTPS — этап 12
   ([16_ci_docker.md](16_ci_docker.md)).

## Принятые решения

- **Автозапуск не нужен на ПК.** Здесь бот запускается вручную, а `--health`
  и лог в файл закрывают потребность «понять, что не так». Для NAS/VPS
  автозапуск дают Docker (`restart: unless-stopped`) или systemd — этап 12.
- **Health-check только читает.** Он не создаёт заметок и не тратит токены
  LLM: проверяет настройки, доступность хранилища, наличие зависимостей.
  Глубокая проверка модели осталась в `--check-llm` — её запускают осознанно.
- **Копия без секретов.** В zip не попадают `.env`, `.obsidian` (в настройках
  плагина лежит ключ REST API), `state/rag`, `state/logs`. Цена: после
  восстановления нужно заново включить плагин и вписать ключ. Выигрыш: копию
  можно хранить на сетевом диске, не думая об утечке.
- **Ротация по числу копий, а не по дате.** Просто и предсказуемо:
  `BACKUP_KEEP` последних файлов; старые удаляются после успешной записи новой.
- **Каталог копий не внутри хранилища.** Проверяется на входе: иначе копия
  попала бы в следующую копию и росла лавиной.
- Отклонено: `robocopy`/`Compress-Archive` в PowerShell — не переживёт перенос
  на NAS (Linux), а `zipfile` из стандартной библиотеки работает везде.

## Как проверить

```powershell
cd E:\FOLDER\TG-OBS\TG_2_Obsidian
.\.venv\Scripts\python.exe -m unittest discover -s tests    # на момент этапа 205 тестов, OK

.\.venv\Scripts\python.exe -m app --health
```

Ожидаемый отчёт (проверено 30.10.2026, Obsidian запущен):

```
app.health: хранилище        ok    rest: доступен; vault: доступен
app.health: LLM              ok    аккаунтов 3, моделей 4 (...)
app.health: RAG              ok    зависимости на месте, индекс: есть
app.health: аудит            ok    ...\state\audit
app.health: копии            warn  BACKUP_DIR не задан: команда --backup недоступна
app.health: доступ           ok    http://127.0.0.1:27123 — только этот компьютер
app.health: лог              ok    ...\state\logs\app.log
app.health: запись           ok    реальная запись в хранилище разрешена
health OK
```

```powershell
# копия и проверка содержимого
$env:BACKUP_DIR='E:\FOLDER\TG-OBS\backups'
.\.venv\Scripts\python.exe -m app --backup
# → ...\backups\tg-obs-backup-YYYYmmdd-HHMMSS.zip
```

Внутри: `vault/...` (заметки), `state/audit/...`, `backup-info.txt`;
`.obsidian` и `.env` отсутствуют. При третьем запуске с `BACKUP_KEEP=2`
остаются два самых свежих файла.

Лог: `state/logs/app.log`, рядом `app.log.1`…`app.log.5` при росте до 2 МБ.

## Риски и откат

- **Копия не заменяет синхронизацию.** С этапа 14 копии делаются сами, пока
  бот запущен ([15_auto_backup.md](15_auto_backup.md)); если бот месяц не
  запускали, копий за этот месяц нет — `--health` покажет возраст.
- **Восстановление вручную.** Распаковать `vault/` поверх хранилища при
  закрытом Obsidian; `state/audit/` — в `state/audit`. Плагин Local REST API
  и ключ придётся включить заново (их нет в копии).
- **Копия в момент записи.** Файл может попасть в архив в момент правки;
  заметки пишутся через временный файл и `os.replace`, поэтому половины
  заметки в копии не будет.
- **Лог растёт при `DEBUG`.** Ротация ограничивает 2 МБ × 5, но `DEBUG`
  стоит включать на время разбора.
- **Откат.** `LOG_FILE=` (только консоль), `BACKUP_DIR=` (копии отключены),
  команды `--health`/`--backup` необязательны; код откатывается возвратом
  `app/logging_setup.py`, `app/health.py`, `app/backup.py`, `app/__main__.py`,
  `app/config.py`.
