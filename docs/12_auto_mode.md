# Этап 10: REST первым, файлы vault — резерв

## Этап

Этап 10 — автоматическое переключение между Local REST API и прямым доступом
к файлам. Дополняет режимы из [06_vault_mode.md](06_vault_mode.md) и решения
ADR-26, ADR-42.

## Цель

Сделать так, чтобы:

- по умолчанию бот работал через REST API (полноценный поиск Obsidian, алиасы,
  теги), пока Obsidian запущен;
- если Obsidian закрылся, плагин выключился или REST ответил `5xx`/таймаутом,
  бот не показывал пользователю ошибку, а продолжал работу с `.md`-файлами;
- возврат к REST происходил сам, без перезапуска бота;
- ответы самого хранилища (`404`, `409`) не повторялись на другом бэкенде —
  иначе обошлась бы защита от дублей.

## Что сделано

- `app/obsidian.py`:
  - новый `FailoverClient` — обёртка над двумя бэкендами `ObsidianBackend`.
    Все методы интерфейса (14: `health`, `search`, `list_notes`,
    `list_folders`, `create_folder`, `rename_folder`, `delete_folder`,
    `delete_note`, `copy_note`, `move_note`, `folder_exists`, `note_exists`,
    `read_note`, `write_note`) идут через `_dispatch()`;
  - `_dispatch()` сначала пробует REST. Переключение — только на временной
    ошибке по `app.retry.is_transient()`: сеть, таймаут, `429`, `5xx`.
    `ObsidianError` с `404`/`409`/`400` пробрасывается без переключения;
  - после сбоя REST помечается недоступным на `OBSIDIAN_FAILOVER_SECONDS`
    (по умолчанию 30 с): следующие вызовы сразу идут в файлы, без ожидания
    таймаутов. Когда пауза истекла, REST проверяется снова сам;
  - `backends_status()` — состояние обоих бэкендов для `--check-obsidian`;
  - `create_obsidian_client()` собирает клиент по режиму: `vault` — только
    файлы, `rest` — только API, `auto` — API + резерв, если заданы и ключ,
    и путь. В `auto` без ключа REST работать не может, поэтому используется
    `VaultClient` с предупреждением в лог.
- `app/config.py`:
  - `effective_obsidian_mode` в `auto` теперь означает основной, а не
    единственный бэкенд: `rest`, если задан `OBSIDIAN_API_KEY`, иначе `vault`;
  - `obsidian_fallback_enabled` — оба бэкенда доступны;
  - новая настройка `OBSIDIAN_FAILOVER_SECONDS` (1–600, по умолчанию 30);
  - в сводке для логов режим `auto` печатается как «rest + резерв vault».
- `app/__main__.py` — `--check-obsidian` в режиме `auto` показывает состояние
  REST и файлов отдельными строками.
- `tests/test_vault_client.py` — 7 тестов `FailoverClientTests`: REST первым,
  переход на файлы при сетевой ошибке, отсутствие повторов внутри паузы,
  повторная проверка REST после паузы, `404` не уходит в файлы, флаг
  `overwrite` сохраняется при записи, отчёт о состоянии бэкендов. Тесты
  режимов обновлены под новые правила `auto`.

## Внешние действия

Одно действие выполнено в рамках этапа: в `.env` режим переключён с
`OBSIDIAN_MODE=vault` на `OBSIDIAN_MODE=auto` (одна строка, обратимо).
Остальное не требовалось: код и тесты выполнены на тестовом хранилище
`E:\FOLDER\TG-OBS\TG-OBS-vault-test`, реальные секреты не менялись.

Чтобы пользоваться приоритетом REST, `OBSIDIAN_VAULT_PATH` и
`OBSIDIAN_API_KEY` должны быть заполнены оба — иначе резерва не будет
(без пути) или REST не будет работать (без ключа). Obsidian при этом можно
запускать и закрывать когда угодно: бот подстроится сам.

Если нужно вернуть прежнее поведение — `OBSIDIAN_MODE=vault` и перезапуск.

## Принятые решения

- **REST первым, файлы вторым.** Пользователь выбрал приоритет REST API:
  он даёт поиск Obsidian по алиасам и тегам. Файлы остаются страховкой, а не
  основным режимом. Прежнее значение `auto` («vault, если задан путь»)
  заменено — иначе включить приоритет REST было бы нечем. Явные `rest` и
  `vault` не изменились, старые `.env` с ними работают как раньше.
- **Переключение только на временных ошибках.** `404` и `409` — это ответ
  хранилища, а не сбой связи. Повтор такого запроса на файлах обошёл бы
  проверку «заметка уже существует» и мог создать дубль. Использован уже
  существующий `is_transient()` из этапа 9, без второй классификации ошибок.
- **Пауза вместо проверки на каждый вызов.** Если REST лежит, каждый запрос
  иначе ждал бы три повтора по ~1,5 с. 30 секунд — компромисс: бот быстро
  работает с файлами, но замечает возвращение Obsidian без перезапуска.
- **Отдельный класс, а не правка двух клиентов.** `FailoverClient` не знает,
  как устроены REST и файлы, и не дублирует их логику; откат — вернуть
  `create_obsidian_client()` к выбору одного бэкенда.
- **Отклонено: два процесса/два бота** под разные режимы — сложнее запускать
  и синхронизировать. **Отклонено: failover по `health()` перед каждым
  запросом** — лишний HTTP-запрос на каждое действие и та же задержка.

## Риски и откат

- **Общий путь у двух бэкендов.** Резерв работает только если
  `OBSIDIAN_VAULT_PATH` указывает на то же хранилище, которое отдаёт REST.
  Иначе бот прочитает один файл, а запишет другой. В `.env` это один и тот же
  тестовый vault.
- **Запись при обрыве связи.** Если REST принял `PUT`, но ответ потерялся,
  `FailoverClient` повторит запись в файл без `overwrite` и получит
  «заметка уже существует». Дубля не будет, но пользователь увидит ошибку.
  Повтор записи на втором бэкенде — осознанный выбор: иначе любая сетевая
  помеха при создании заметки означала бы потерю текста.
- **Разные движки поиска.** Пока REST доступен, поиск идёт движком Obsidian;
  после переключения — по словам, без алиасов и тегов. Результаты могут
  отличаться, это описано в [06_vault_mode.md](06_vault_mode.md).
- **Задержка первого запроса после сбоя.** Если REST отказал в соединении —
  до ~1,5 с (три повтора чтения), дальше 30 секунд быстрого режима. Если REST
  не отвечает, а висит, ждать придётся до таймаута: `TIMEOUT_SECONDS` (10 с)
  × `OBSIDIAN_RETRY_ATTEMPTS` (3). Для мгновенного переключения поставьте
  `OBSIDIAN_RETRY_ATTEMPTS=1`.
- **Откат.** Вернуть `OBSIDIAN_MODE=vault` (или `rest`) в `.env`; код —
  возвратом `app/obsidian.py`, `app/config.py`, `app/__main__.py` и тестов
  к предыдущему коммиту. Данные не мигрируют: оба режима работают с одними
  и теми же `.md`-файлами.
